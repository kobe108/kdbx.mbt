# 功能清单（一次一个功能）

这份清单把 MVP 拆成能独立验收的小功能。每个功能单独提交一次，做完再挑下一个，
避免一次改一大片导致"哪里坏了说不清"。

## 工作节奏

每个功能都按同一套流程走：

1. **先定验收标准**：这一项做完之后，什么命令能证明它是对的。
2. **先写测试向量**：能用官方向量（FIPS、RFC、规范附录）就用官方向量；
   向量用独立实现（Python hashlib 等）核对过再写进测试，不凭记忆手抄。
3. **再写实现**，跑到 `moon test` 全绿。
4. **收尾三连**：`moon fmt`、`moon check`（无警告）、更新本文件与 README 的进度表。
5. **一次提交**，提交信息写清楚"这个功能解决了什么"。

## 现在在哪一步

F1 到 F7 已完成，共 18 个测试用例，`moon check` 无警告。
下一个功能是 **F8 头部完好性校验**：用真实 `.kdbx` 文件验签，
也就是第一次"真的碰上别人的文件"。

### AES-KDF 实测吞吐

轮数是密码库抗暴力破解的代价，也直接决定打开文件要等多久，所以这个数字要测不要猜：

| 构建 | 100 万轮耗时 | 折算吞吐 | 600 万轮（KeePass 常见值） |
| --- | --- | --- | --- |
| release | 约 2.6 秒 | 约 38 万轮/秒 | 约 16 秒 |
| debug | 约 17 秒 | 约 5.8 万轮/秒 | 约 1.7 分钟 |

6000 万轮的库（老版本 KeePass 的默认档）在 release 下约 2.6 分钟。
这个量级可以接受但不宽裕，因此 F7b 把优化列为可选项：
热点在每轮 `ShiftRows` 的 16 字节拷贝与数组边界检查上。

## 向量来源与核对方式

- F2、F3：KeePass 官方 KDBX 4.1 规范里的字节序列。
- F4、F5：FIPS 180-4（SHA-2 示例）与 RFC 4231（HMAC 测试用例）。
- F6：FIPS-197 附录 B、C 的 AES 示例向量。
- F6 的其余向量：用 .NET 的 AES 实现（ECB、无填充）生成，作为独立参考实现交叉验证；
  S 盒由定义在 Python 中算出（GF(2^8) 求逆加仿射变换），不手抄 256 字节表。
- 教训：S 盒最初只用 5 个抽查值验证，结果漏掉了索引 0x1b 的一个错值，
  直到 FIPS-197 向量失败才暴露。现在测试会**按定义重算全部 256 个格子**逐一比对。
  凡是查表型常量，抽查都不算验证。
- 定位方法：先用 Python 复刻同样的算法结构（[work/aes_check.py](../../work/aes_check.py)），
  它算出的就是标准答案，因此可以确定"算法正确、文件抄错"，
  再用脚本逐格比对（[work/check_sbox.py](../../work/check_sbox.py)）一次定位到错处。
- F7 起：KeePass 与 KeePassXC 的公开测试库文件（按许可证要求不随仓库分发，
  集成测试按固定提交号下载）。
- 所有向量在写进测试前，用 Python 的 `hashlib` / 独立实现交叉核对。
